# A-FRAME KG — административная панель, этап 1

Работа выполнена внутри существующего приложения. Сохранены `/kg/admin`, `/ru/admin`, `/en/admin` и существующие `admin/[section]`.

## Аудит

| Область | Существующая архитектура |
| --- | --- |
| Framework | Next.js 16.4, App Router, Cache Components, React 19, TypeScript. Изучены локальные руководства установленного Next.js. |
| Данные | PostgreSQL, Prisma 7 с `@prisma/adapter-pg`; существующие модели и связи переиспользованы. |
| Авторизация | Хешированные серверные сессии, HttpOnly/SameSite cookie, проверка активности, Telegram OTP для ADMIN. Сессии ADMIN без `adminVerifiedAt` отклоняются. |
| Роли | USER, OWNER, ADMIN. Первоначальный администратор создаётся существующей доверенной командой `db:create-admin`. Регистрация не выдаёт ADMIN. |
| Server Actions | Существующие валидация, транзакции и AuditLog; добавлен общий серверный rate limit административных изменений. |
| Бронирования | Блокировки строки домика и PostgreSQL exclusion constraint для пересечений дат; сохранены PENDING, CONFIRMED, CANCELLED, COMPLETED, REJECTED. |
| Фотографии | Существующий OWNER upload проверяет владение, Origin, размеры, формат и декодирование; Sharp преобразует фото в WebP. Административный CRUD относится к этапу 2. |
| Локализация | KG/RU/EN: JSON и существующие переопределения Translation в БД. Прямая серверная запись JSON не добавлена. |
| Дизайн | Manrope, фирменный логотип, тёмные зелёные поверхности, существующие Radix Select/Popover; для панели установлен Lucide. |

## Реализовано

- Отдельный защищённый AdminLayout в `(administration)`, без публичных Header/Footer. Существующие страницы перемещены с сохранением URL.
- Sidebar: активный раздел, сворачивание, доступный мобильный dialog, ссылка на сайт. Аналитика и поддержка обозначены как последующие этапы; сохранён существующий раздел удобств.
- Topbar: breadcrumbs, глобальный поиск с задержкой и отменой устаревших запросов, обновление данных, языки, уведомления текущего ADMIN, профиль и реальный выход.
- Dashboard: десять показателей, графики бронирований и выручки, распределение статусов, популярные направления/домики, последние бронирования и быстрые переходы.
- Периоды 7/30/90/365 дней, произвольный диапазон до 366 календарных дней. Границы в `Asia/Bishkek`, включая весь последний день. Невалидные и будущие диапазоны показывают ошибку.
- Последние бронирования: серверный поиск, статус, пагинация по 6 строк; номер страницы ограничивается фактическим количеством страниц. Поиск домиков и пользователей работает также в существующих списках.
- Нули и Empty States при отсутствии записей, skeleton при загрузке и локализованная ошибка с повторной загрузкой. Ошибка БД не превращается в ложные нули.
- График имеет доступную таблицу исходных дневных агрегатов. Формы используют существующие Radix-примитивы и календарь для исторического диапазона.

Проверка ADMIN есть в layout, страницах и слое данных. Она не зависит от видимости меню. Поиск проверяет роль самостоятельно; административные действия сохраняют собственную проверку прав. Next.js проверяет Origin/Host для Server Actions.

## Правила статистики

Объекты и аккаунты — текущие общие количества. Бронирования, распределение статусов, популярность и платежи — за выбранный период. Активные брони — CONFIRMED с датой выезда после сегодняшнего дня. Ожидающие заявки — PENDING.

Домики `isDemo=true` и брони `DEMO-*` исключены из коммерческих показателей. Выручка и количество подтверждённых платежей учитывают PAID в KGS с датой оплаты и ID транзакции, исключают `AWAITING_CONFIGURATION`, REFUNDED, FAILED, PENDING и другие валюты. Агрегаты используют Decimal в БД; суммы отображаются до двух знаков.

Dashboard различает отсутствие настройки Finik и наличие серверной конфигурации. Ключи не передаются клиенту. Наличие конфигурации не подтверждает внешнюю транзакцию. Административного действия произвольного назначения PAID нет.

## Модели Prisma

Данные Dashboard: `Cabin`, `Booking`, `Payment`, `User`, `OwnerProfile`, `Location`, `Region`, `CabinImage`. Оболочка и защита: `Session`, `Notification`, `AuthThrottle`. Локализация: `Translation`; важные существующие изменения: `AuditLog`. Для этого этапа новые модели не создавались.

## API и Server Actions

Новый `GET /api/admin/search?locale=ru&q=...`: обязательная активная сессия ADMIN с OTP, 401/403 для остальных, валидация языка/строки, 120 запросов за 15 минут на администратора. До 5 результатов каждого типа: домики, брони, пользователи. Ответ содержит только название, тип, ID и внутренний URL, без email, телефонов и паролей. Ответы `private, no-store`.

Новые административные Server Actions не создавались. В существующих `referenceAction`, `userAdminAction`, `ownerAdminAction`, `cabinAdminAction`, `bookingAdminAction`, `reviewAdminAction`, `translationAdminAction`, `settingsAdminAction`, `notificationAdminAction` добавлен общий лимит 100 изменений за 15 минут на администратора.

## Проверки

Итоговые результаты будут записаны после завершения браузерного прогона. Операции тестируются в новой случайной схеме `aframe_qa_*`; удаляется только эта схема. Основные записи приложения не удаляются. Telegram, Google и Finik в тестовом окружении отключены.

## Интеграции и оставшиеся этапы

Telegram-вход ADMIN использует существующие серверные `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ADMIN_CHAT_ID`, `ADMIN_OTP_SECRET`. Отправка реального OTP этим этапом не проверялась. Finik появился в рабочем дереве во время выполнения этапа; реальные оплата, возврат и доставка webhook не проверялись этим этапом. Действующие секреты, ранее попавшие в `.env.example`, следует заменить у провайдеров.

- Этап 2: полный административный CRUD домиков, фотографии, удобства, доступность, направления и расширенная модерация.
- Этапы 3–5: календарь загрузки, история статусов/платежей, полноценные таблицы пользователей и владельцев, центр уведомлений, расширенная модерация отзывов.
- Этапы 6–7: аналитика с CSV, Support с реальным каналом ответа, публикация переводов, расширенные настройки и права. AuditLog не имеет административного API изменения/удаления; защита журнала отдельной ролью БД относится к усилению эксплуатации.

Существующие разделы отображаются в новой оболочке и сохраняют серверные действия. Их полная переработка по общему ТЗ ещё не заявляется выполненной.
